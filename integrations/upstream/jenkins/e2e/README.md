# Native Jenkins HPI integration acceptance

This verification **builds the actual HPI**, loads it into a disposable
`jenkins/jenkins:lts-jdk21` controller with Warnings NG and Pipeline plugins,
then schedules `darkmoonScan` through a real Pipeline job on an independent
`jenkins/inbound-agent:jdk21` container (Node 22 installed **only** on the
agent). The agent uses `/home/jenkins/agent workspace` and OSS paths containing
spaces to prove remote `FilePath.copyFrom` and process argument quoting.

The packaged HPI includes `darkmoon-ci.cjs` and its pinned dependency via a
Maven `generate-resources` build step; there is no dependence on
`~/darkmoon-client`, a global CLI, or `darkmoon-client-0.1.0.tgz`.

## Reproduce

Required: Java 21, Maven 3.9+, Node/npm 18+, Docker Engine, Python 3, curl
and network access for **build dependencies only**.

```bash
cd integrations/upstream/jenkins
mvn -B -ntp clean verify
bash e2e/run-e2e.sh
```

The driver uses randomly named Docker containers, images and an isolated Docker
network; it binds the Jenkins HTTP port to 127.0.0.1 only and cleans up on
completion/failure. `KEEP_NATIVE_CONTAINERS=1` leaves failed containers for
manual diagnosis. Do not run on a shared Jenkins installation.

## Scenarios

- Nonempty high findings: FAILURE, one Warnings NG SARIF issue, safe named artifacts
- Zero findings: SUCCESS, zero Warnings NG issues, no stale prior issue
- Nonempty findings below thresholds: SUCCESS, SARIF issue ingested
- Medium findings with failOn=high/unstableOn=medium: UNSTABLE
- Missing/malformed/nonarray findings and a foreign finding/campaign identity:
  FAILURE with no successful empty SARIF
- Missing or malformed campaign record, failed/stopped assessment and a running
  campaign that times out: FAILURE
- Ambiguous concurrent campaign records: FAILURE (no newest-mtime fallback)
- Missing requested report after a previous build wrote one: only the current
  campaign's SARIF and CLI log are eligible; never archive a stale report
- Missing Jenkins Secret Text credential: FAILURE before running CLI
- Agent with Node intentionally removed from PATH: FAILURE with safe error

All fixtures are generated by `engine-standin.sh` on the isolated agent. The
stand-in never connects to the target and performs no real assessments.
The native driver checks the plugin manager's **active HPI**, waits for the
separate agent to be online, checks build status and Warnings NG issue totals,
reads every archived artifact for synthetic secret/evidence markers, verifies
no unrelated workspace file is archived, and asserts a copied CLI exists under
the remote agent workspace with spaces.

The dedicated JenkinsRule suite separately simulates a downstream HTTP 401
findings-read failure, confirming it cannot publish an empty SARIF or leak the
body. The native agent's workspace is reused deliberately between cases.

## Boundaries

The Docker images are upstream Jenkins LTS and inbound-agent images; their
specific versions/digests are captured at runtime in CI rather than inferred
from the floating tags. This test exercises the packaged CLI's local OSS contract
and Jenkins Pipeline/Warnings NG host, not a vendor-licensed Pro API, an actual
assessment, remote Docker/Kubernetes Jenkins agents or Windows agent execution.
Controller and workspace state are intentionally disposable. There is no
deployment or external notification.
