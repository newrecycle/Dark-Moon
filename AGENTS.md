# DarkMoon

Autonomous AI-powered penetration testing platform. Architecture: **Hermes** (the LLM brain, running on the host) → **Dark-Moon MCP** (security gatekeeper + privacy gateway) → **single `darkmoon` Docker container** (toolbox with 50+ real offensive tools + the MCP server baked in). The LLM never executes tools directly and never sees real IPs/creds — values are tokenized to placeholders server-side before the model sees them (privacy gateway). Agents live in `conf/agents/*.md`; config is rendered at container start by `conf/bootstrap.py` using `conf/opencode-config.py`.

## Dev environment
- Requires Docker + Docker Compose v2. Most build/test commands need Docker.
- Python 3.12, PyYAML (CI pins `PyYAML==6.0.3`), Node.js (CI `NODE_VERSION=24`).
- `mcp/` uses `uv` + `pytest`; root `tests/` uses `unittest`. Keep the two separate.
- LLM provider config lives in `.opencode.env` (generated by `install.sh`, chmod 600, holds API keys — do NOT commit). Hermes is the brain; this file only seeds the toolbox env.

## Build & test
Fast (no Docker), run from repo root:
```
python -m unittest -v tests.test_agent_config tests.test_production_bootstrap tests.test_compose_security tests.test_reproducibility
```
MCP privacy + local-executor unit tests:
```
cd mcp && uv run --with pytest --with pydantic --with fastmcp --with docker python -m pytest -q
```
Integration (spin up the stack — slow, need Docker + images):
```
bash tests/test_production_stack.sh           # full single-container bootstrap + real darkmoon_* MCP round-trip
bash tests/test_docker_mcp.sh                 # stock MCP protocol fixture (single container)
```
Compose topology check (no build):
```
docker compose -f docker-compose.yml config
docker compose -f docker-compose-dev.yml config
```
Repo invariant gate: `bash tools/check-no-regression.sh`. CI also runs `shellcheck -x` on the shell scripts.

Install / launch the backend:
```
./install.sh            # prepare env (.opencode.env, bind dirs); the LLM brain is Hermes, not an in-container OpenCode
./darkmoon.sh up        # bring the single darkmoon container up; waits for the MCP on 127.0.0.1:8000
./darkmoon.sh status    # show compose status + probe the MCP port
./darkmoon.sh down      # stop the container
./darkmoon.sh mcp <module>   # run `python -m src.<module>` inside the container (e.g. `mcp healthcheck`)
```
The Hermes entrypoint is the `plugin/` package: `hermes plugins install <path-or-url>` then `hermes plugins enable darkmoon`. The MCP is reached at `http://localhost:8000/mcp` (Streamable HTTP). There is **no `/health` HTTP route** — check readiness via the `darkmoon_health_check` MCP tool or a TCP probe of port 8000.

## Conventions
- **Agents = Markdown** in `conf/agents/*.md`: YAML frontmatter (fields restricted to `model, variant, temperature, top_p, description, mode, hidden, options, color, steps, disable, permission`) + prompt body. `pentest` is the only `primary`; all others are `subagent` (enforced). Permission defaults to least-privilege: `*`: deny, `darkmoon_*`: allow, `pentest` also `task`: allow. Legacy keys (`id, name, primary, secondary, prompt_file, mcp, tools, maxSteps`) are auto-migrated and stripped — never author them.
- MCP tools must be named `darkmoon_*` (tests assert this wildcard). Tools are registered with bare names in `mcp/src/server.py`; the `darkmoon_` prefix comes from the MCP **server key** `"darkmoon"`. Executing them runs tools as **local subprocesses** inside the container (`DARKMOON_EXEC_MODE=local`).
- New MCP workflow → copy `mcp/src/tools/workflows/TEMPLATE.py` (subclass `BaseWorkflow`), expose it in `mcp/src/server.py`; full guide in `mcp/WORKFLOW_GUIDE.md`.
- `conf/plugins/darkmoon-compat.js` is the legacy OpenCode plugin (forces `default_agent=pentest`, registers the MCP as remote). It is retained for the config renderer but is NOT used when Hermes is the brain.
- Model routing env vars (in `.opencode.env`): `DARKMOON_SMALL_MODEL`, `DARKMOON_AGENT_MODELS` (JSON), `DARKMOON_DISCOVER_MODELS=1`.
- `mcp/requirements.lock` is hash-pinned via `pip-tools`; derivable from `mcp/requirements.in`.

## Pitfalls
- **Single container by design.** `docker-compose.yml` (x86_64, prebuilt `ascit/darkmoon:latest`) and `docker-compose-dev.yml` (ARM64, builds `Dockerfile` locally) each define exactly ONE service: `darkmoon`. Tests assert no `opencode`/`opencode-bootstrap`/`docker-proxy`/`darkmoon-mcp` services remain — don't add them back.
- The `darkmoon` container uses `network_mode: host`, so `localhost:8000/mcp` is reachable from the host with no port mapping. Under host networking, `ports:` are ignored.
- **No Docker socket is mounted.** The toolbox runs its tools locally; the docker-audit agent targets *external/host* sockets via local exec, never its own. Security tests fail if `/var/run/docker.sock` appears in any compose volume.
- `darkmoon-settings/` is the **live** runtime state (agents, auth, DB, reports) and is gitignored. `conf/agents/` is canonical/source. Do not hand-edit `darkmoon-settings/agents/*.md` — bootstrap migrates from `conf/agents` and is idempotent.
- Credential-gated agents (aws/azure/gcloud/sql/docker/AD/k8s/Vault) must **not** dispatch on inference — only when a concrete artifact (key/token/metadata) is found or the user authorizes. Never run `tools/lab-tests/run-lab-tests.sh` against a shared prod stack (INC-011); it requires `DARKMOON_TEST_STACK=1`.
- NVIDIA GPU for hashcat needs `--gpus all` + `NVIDIA_DRIVER_CAPABILITIES=compute,utility` (set in Dockerfile); without it hashcat silently falls back to CPU.
- Privacy gateway: never hardcode real IPs/hostnames/creds in agent prompts, workflows, or reports. Use `IP_PRIVATE_001`-style placeholders.
- The local executor kills the whole process group on timeout (`killpg`) so an orphaned background tool can't hang the MCP. Do not reintroduce `docker exec` execution paths.
